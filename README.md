# MIC16_ADC123_USB —— 16 路原始数据，USB 虚拟串口输出

> **一句话：16 路 ADC 采到的每一个点，原封不动地通过 USB 虚拟串口（CDC）送到 PC，
> 每路 20 kHz。**
>
> 没有抽取、没有平均、没有滤波——串口帧里的 16 个 u16 就是那一次 ADC 扫描的原始码值。

## 0. 四个工程的关系（互不覆盖）

| 工程 | 采样率 | 数据出口 | 用途 |
|---|---|---|---|
| `MIC16_ADC123` | 200 kHz | 串口 115200（按需 A/V/d） | 原始工程，**未改动** |
| `MIC16_ADC123_STREAM` | 内部 200 kHz → 输出 2 kHz | 串口 921600 | 100 点平均后上传（带低通） |
| `MIC16_ADC123_RAW` | 2 kHz | 串口 921600 | 1:1 直通，串口版 |
| **`MIC16_ADC123_USB`（本工程）** | **20 kHz** | **USB CDC 虚拟串口** | **1:1 直通，USB 版** |

## 0.1 实测结果（2026-11-23，实物板实测）

**采集 → USB 虚拟串口 → PC 端 Python 接收**，每档跑 8 秒：

| 每路采样率 | 应产帧数 | 板子发出 | PC 收到 | **达成率** |
|---|---|---|---|---|
| 16 kHz | 128,051 | 128,370 | 128,376 | **100.3%** |
| **18 kHz（默认）** | 144,002 | 144,225 | 144,221 | **100.2%** |
| 20 kHz | 160,004 | 155,285 | 154,985 | 96.9% |
| 纯 USB 吞吐（`p` 模式） | — | — | — | **22,031 帧/s = 837 kB/s** |
| **单 USB 线（命令也走 USB）** | — | — | **18,007 fps** | **lost=0 crc=0** |

**结论：这块板子 + USB 全速虚拟串口的稳定上限是 16 路 × 18 kHz（100% 零丢帧）。**
20 kHz 会丢约 3%，所以默认值取 18 kHz。

> 下面各节仍以 20 kHz 举例说明计算关系；实际默认值是 18 kHz，
> 两者只差 10%，公式通用（把 20000 换成 18000 即可）。

本工程只改了 `USER/mic.h`、`USER/mic.c`、`USER/main.c`，新增
`USER/usb_cdc.c`、`USER/usb_cdc.h`；`uart.h` 沿用（命令通道）。

## 1. 两个 COM 口，别搞混

上电后 PC 上会出现**两个串口**：

| 端口 | 用途 | 波特率 | 连在哪 |
|---|---|---|---|
| **命令口** | 发 `A`/`V`/`c`/`x`/`w`/`u`/`?` | **115200**（真波特率） | USB-TTL 模块 → PA9/PA10 |
| **数据口** | 只输出 38 字节二进制帧 | **虚拟的**，填什么都行 | USB 线 → PA11/PA12（板载 Type-C） |

**PC 端跑 `raw_recv.py` 时要连"数据口"那个 COM 号。**

> 数据口的波特率是虚拟的：CDC 的 `SET_LINE_CODING` 只是把参数转给设备，
> 真正速度由 USB 总线决定。所以脚本里 `--baud` 写多少都不影响速度。

## 1.1 只用一根 USB 线（推荐形态）

**命令也可以从 USB 数据口发**，所以串口（PA9/PA10）变成纯可选：

| 通道 | 用途 | 必须吗 |
|---|---|---|
| 板载 USB-C → 数据口 COM5 | 收 38 B 原始帧 + **发命令** | ✅ 必须 |
| CH343 → PA9/PA10 → 命令口 COM4 | 发命令、看回显 | ❌ 可选 |

**怎么发命令**：用任意串口工具打开数据口，写一个字符即可（不分大小写）：

```
c   开始原始数据流        x   停止
u   USB 状态（枚举/中断计数/寄存器）
w   流状态（fs/sent/drop/blocks/lost）
A / V / d   统计 / 诊断 / 导出
8k 16k 18k 20k 32k ... 200k   切换采样率
p   纯 USB 吞吐测试
```

注意：
- 从 USB 口发的命令，**回显仍然走串口**（COM4）；没有串口时靠"数据有没有开始流"判断；
- 数据口是二进制的，**必须用脚本或 HEX 模式看**，文本模式是乱码；
- 同一个 COM 口同一时刻只能被一个程序占用。

## 1.2 看数据的四种方式（`tools/raw_recv.py`）

| 想做什么 | 命令 | 说明 |
|---|---|---|
| 屏幕滚动看码值 | `--text` | 10 Hz 挑一帧显示；`--every N` 可调（N=20 → 约 900 行/秒） |
| 存 CSV 用 Excel 看 | `--csv out.csv` | 每帧一行，18 kHz → 18,000 行/秒 |
| 听声音 | `--wav ch1.wav --wav-ch 1 --fs 18000` | `--fs` 要和板子一致，否则音调不对 |
| 实时波形 | `--plot` | PC 端重绘开销大，会降到约 10k fps |
| **生成波形图** | `--png wave.png --png-ms 50` | 16 路叠成一张图，可放进报告 |
| 启动数据流 | `--start` | 自动发 `c`，不用手动发命令 |
| 长时间零丢帧记录 | `--save rec.bin` | 每帧 32 B，约 2.4 GB/小时 |

> **显示频率 ≠ 传输速率**：`--text` 每秒只打印 10 帧给人看，但后台 18,000 帧/秒
> 全部传到了 PC（实测 lost=0）。要"全部"就落盘（`--csv`/`--save`），
> 往终端打 18,000 行/秒只会让终端卡死并开始丢帧。

## 2. 硬件接线

| 信号 | 引脚 | 说明 |
|---|---|---|
| USB D- | **PA11** | 接到 Type-C 的 A7/B7 |
| USB D+ | **PA12** | 接到 Type-C 的 A6/B6 |
| GND | GND | 必须共地 |
| 命令串口 TX | PA9 | 接 USB-TTL 的 RXD |
| 命令串口 RX | PA10 | 接 USB-TTL 的 TXD |

**两个关键冲突已经处理好了：**

- USB 的 VBUS 检测脚是 **PA9**（正好是 USART1_TX）→ 代码里置 `GCCFG.NOVBUSSENS` 关掉，
  PA9 还给串口；
- USB 的 ID 脚是 **PA10** → 代码里强制设备模式（`GUSBCFG.FORCEDEVMODE`），不采样 ID。

所以 **USB 只用 PA11/PA12，串口完全不受影响**。

> 前提：板上的 Type-C 必须真的接到 PA11/PA12。先用万用表量一下
> Type-C 的 A6/B6 ↔ PA12、A7/B7 ↔ PA11。不通的话要从排针飞线到一个小 USB 座。

## 3. 数据速率

```
每路 20,000 Hz × 16 路 = 320,000 点/秒
每帧 38 B（2 头 + 2 帧号 + 32 数据 + 2 CRC）
20,000 帧/s × 38 B = 760,000 B/s = 760 kB/s
760 kB/s ÷ 1,000 kB/s（USB CDC 实测上限） = 76%
```

| 每路采样率 | 数据率 | 占 USB 实测带宽 | 建议 |
|---|---|---|---|
| 16 kHz | 608 kB/s | 61~76% | 最稳 |
| **20 kHz（默认）** | **760 kB/s** | **76~95%** | 推荐 |
| 24 kHz | 912 kB/s | 91%~110% | 上限，看运气 |
| 26 kHz | 988 kB/s | 99%~124% | 理论极限，会丢帧 |

`c` 命令里会检查：当前 fs 超过 **24 kHz** 就拒绝启动，提示上限。

### 3.1 如果目标就是"把音频传出来"，怎么选采样率

| 每路采样率 | 16 路数据率 | 音频带宽（fs/2） | 评价 |
|---|---|---|---|
| 16 kHz | 608 kB/s | 8 kHz | 电话音质，最稳 |
| **20 kHz** | **760 kB/s** | **10 kHz** | **语音清晰，推荐** |
| 24 kHz | 912 kB/s | 12 kHz | 上限，看主机 |
| 44.1 kHz | 1.68 MB/s | 22 kHz | ❌ 16 路装不下 |
| 48 kHz | 1.82 MB/s | 24 kHz | ❌ 16 路装不下 |
| **48 kHz × 8 路** | 912 kB/s | 24 kHz | ✅ 减到 8 路可以 |

> 麦克风放大模块的带宽一般是 20 Hz~20 kHz，20 kHz 采样能覆盖到 10 kHz——
> 语音、敲击、环境声都够听清楚，但不是 Hi-Fi。
> 要 44.1/48 kHz 的"全音频"，16 路在这条 USB 全速链路上做不到，只能减通道数或换硬件。

## 6. 帧格式（38 字节，小端）

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 1 | `0xAA` |
| 1 | 1 | `0x55` |
| 2 | 2 | 帧号 `seq`（u16，回绕） |
| 4 | 32 | 16 × u16 **原始码值**（0..4095） |
| 36 | 2 | CRC16/CCITT-FALSE，覆盖 `[2..35]` |

换算：`mV = code × 3300 / 4096`，1 LSB ≈ 0.806 mV。

## 7. 上电检查清单

1. **设备管理器**是否出现新的 COM 口（Windows 自带 CDC 驱动，不用装）；
2. 命令口发 `u`，应回 `usb=configured ...`；
   - 回 `not configured` → 枚举没成功，看第 9 节；
3. 命令口发 `c`，回 `raw on: 20000 Hz x 16 ch 1:1 ...`；
4. PC 端跑 `raw_recv.py` 连**数据口**，看 `fps` 是否稳定在 20000。

## 8. PC 端

```bash
pip install pyserial

# 看帧率（数据口，比如 COM7）
python tools/raw_recv.py COM7

# 落盘 10 秒
python tools/raw_recv.py COM7 --save raw.bin --seconds 10

# 存成 16 声道 WAV（可以直接播放/送人听）
python tools/raw_recv.py COM7 --wav mic16.wav --fs 20000 --seconds 10

# 只存第 3 路（单声道，最容易"听"）
python tools/raw_recv.py COM7 --wav ch3.wav --wav-ch 3 --fs 20000 --seconds 10

# 实时画 16 路（需要 pyqtgraph）
python tools/raw_recv.py COM7 --plot
```

> `--fs` 只影响 WAV 头里的采样率，默认 20000，要和板子当前 `MIC_FS_HZ` 一致，
> 否则放出来音调会不对（快放/慢放）。
>
> WAV 里做了去直流（减 2048）×16 放大，所以麦克风的交流信号能正常听；
> 16 声道 WAV 部分播放器不支持，听单声道建议用 `--wav-ch`。

**验收要点：`fps` 必须等于采样率（20000）。** 因为 1:1 直通的定义就是
“帧数 = 采样点数”。

| 现象 | 判断 |
|---|---|
| `fps` = 20000 ± 2，`lost` 不涨 | ✅ 正常 |
| `fps` 明显低、`lost` 猛涨 | USB 带宽不够或被主机调度挤掉 |
| `fps` ≈ 2000 | 采样率被改成了 2k |
| 一帧都收不到 | 连错 COM 口（连到命令口了）/ 没发 `c` |
| `c` 回 `fs too high` | 当前 fs > 24 kHz，先发 `2k` 或上电默认 20k |

## 9. 枚举失败怎么查

| 检查 | 方法 |
|---|---|
| Type-C 是否真接 PA11/PA12 | 万用表量通断 |
| 5V/3.3V 供电 | USB 插上后板子是否上电；ST-Link 的 3.3V 别和 USB 同时供 |
| 48 MHz 时钟 | `PLL_Q=7` 已在 `system_stm32f4xx.c` 里；若改过 PLL 要保证 48 MHz |
| 设备管理器 | 出现"未知 USB 设备(设备描述符请求失败)" → 多半是 D+/D- 接反或 PA9 冲突 |
| D+ 上拉 | OTG_FS 内部自带，软件使能（`DCTL.SDIS=0`），不需要外部电阻 |

> **重要：USB 枚举失败时板子会“失联”，所以命令串口必须保留**——
> 这也是本工程坚持把命令放在 PA9/PA10 的原因。

## 10. 为什么只能到 20~26 kHz

USB 2.0 全速的规范上限：

```
12 Mbps 总线
每 1 ms 帧，批量端点最多 19 个 64 字节包
19 × 64 × 1000 = 1.22 MB/s（理论），实测 0.7~1.0 MB/s
```

所以：

- **不是代码问题**，改 CDC 波特率、优化代码都不会变；
- 要突破必须换 USB 高速（480 Mbps），而 F407 要外挂 ULPI PHY，
  12 根脚里 8 根和 16 路 ADC 冲突 → 必须改板；
- **200 kHz × 16 路（7.6 MB/s）这块板子做不到**，差 6~9 倍。

## 12. 调试注意

| 现象 | 先看什么 |
|---|---|
| 命令口正常、`u` 显示 not configured | 枚举问题，见第 9 节 |
| `u` 显示 configured 但收不到数据 | 没发 `c`；或脚本连的是命令口 |
| `c` 启动后 `w` 里 `drop` 猛涨 | USB 带宽不足，降 `MIC_FS_HZ` |
| 板子反复重启 | 初始化里某个等待超时 + 看门狗；先看命令口有没有反复打印 banner |
| 数据有但 CRC 错 | 线太长/接触不良；USB 全速对线材不算敏感，多半是接插件问题 |

## 13. 实测流程（把"能跑多少"查清楚）

导师要的是**实测数字**，不是理论值。按这个顺序做，一天能出结论。

### 第 1 步：纯 USB 吞吐（不经过 ADC）

```bash
# 命令口（115200）发 p
# 数据口跑 30 秒
python tools/raw_recv.py COM7 --seconds 30
```

记录 `fps`，**字节率 = fps × 38**。

| 指标 | 填这里 | 说明 |
|---|---|---|
| 实测 fps | ________ | `raw_recv.py` 打印的 fps |
| 实测字节率 | ________ kB/s | fps × 38 ÷ 1000 |
| 换算成位率 | ________ Mbps | ×8 ÷ 1000 |
| 理论值 | 1220 kB/s / 9.76 Mbps | USB 全速批量上限 |

> 如果实测只有 60~70 kB/s，说明端点没续上包（每 1 ms 只发 1 包），
> 那是代码问题；本工程的发送完成中断里会立刻续包，正常应该 700~1000 kB/s。
